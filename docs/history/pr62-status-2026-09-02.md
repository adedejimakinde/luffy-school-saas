## The one real defect the rebase introduced

The review had changed the template from `card.is_revised` to
`card.version > 1`, because **on the old base no such field existed** — Django
resolves a missing name to the invalid-variable default, so the "Revised" badge
could never print. Invisible until a second version exists, at which point the
reprinted card is indistinguishable from the one already in a parent's hand,
which is the single thing the badge exists to prevent.

That fix was right against the old base and **wrong against this one.** Task 8
added `ReleasedCard.is_revised`, put it on `ReportCardOut`, and its docstring
calls it *"the only source of that word"*. The comment left beside that line
asserted `ReportCardOut` carries no such flag — **false the moment task 8
landed**, which is the same false-premise trap the review commit was written to
close.

**The lesson worth keeping: a fix's justification can go stale even when the fix
still produces the right output.** `version > 1` would still have printed
correctly today; it re-implements in a template a rule the model deliberately
centralised, and task 8's docstring names the case that separates them — a child
placed into a term after it was released gets her first card through the
revision path, at version 1, and must not be told it corrects something she
never received.

The template reads `card.is_revised` again. `html_at_version()` now moves
`version` and `is_revised` **together**, as `card_payload()` emits them; a test
overriding only `version` would have gone quietly green against a page that
never printed.

## The six review findings, for the record

1. **`card.is_revised` was on no schema** — the badge could never print. (Now
   superseded by the rebase fix above.)
2. **Assessment columns were keyed on the display name alone.** `max_score` is
   per `(term, subject, name)`, so Mathematics' "Exam" out of 120 and English's
   "Exam" out of 100 are two assessments; collapsed into one column, two equal
   marks print as equal performance and are not. Keyed on `(name, max_score)`
   now, header carries the maximum, subject total prints its denominator.
3. **The claimed print order was false.** Docstring and `docs/report-card-pdf.md`
   both said "alphabetical today"; `cards._assessments_for()` says the opposite
   in as many words — it orders by `(subject name, id)` *because*
   `Assessment.Meta.ordering` ends in `name`. **Whoever fixes #42 would have
   started from a false premise.**
4. **Attendance was gated on `days_open` alone.** The three columns are
   independently nullable, so `days_present=52, days_open=None` is a row the
   database permits, and it printed a bare dash — the page saying "nobody kept a
   register" about a child whose attendance was recorded.
5. **`a_card_pdf_knows_its_own_size` checked only that `byte_size` was set, not
   that it was true.** Now compared against `Length("content")`, keeping the
   `IS NOT NULL` beside it, because with `byte_size` null the comparison is null
   and Postgres counts a null CHECK as satisfied — dropping it would have
   loosened the constraint while appearing to tighten it.
6. **`or "unknown error"` could never fire** — the f-string always carries at
   least `"<TypeName>: "`.

## Noted on #56 rather than fixed here

**`results.cards.cards_on()` has no caller anywhere in the repository** — only
its definition and its `__all__` entry. Its docstring, written in task 8, says
"task 7's PDF job walks a whole class". **It does not** — it renders one card
per job, deliberately, because `acks_late` means a worker killed on the
forty-fourth card hands the message back, and `visibility_timeout` is 300
seconds.

The walk is the missing enqueuer, which is what #56 is about. Two consequences
recorded there:

- **The enqueuer wants `(schema_name, card_id)`, not prefetched cards** — the
  worker re-reads the card in its own transaction anyway, which is what makes
  the job idempotent. But it **must keep** task 8's
  `DISTINCT ON (student_membership_id) … ORDER BY version DESC`, or a 45-child
  class enqueues 46 jobs and a superseded version 1 gets rendered and sent home.
- **The premise to avoid inheriting is that a batch *reader* implies a batch
  *job*.** It does not, and the queue settings are the reason.
